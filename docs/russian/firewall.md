# 🛡️ Firewall (демон)

> 🌍 **Язык:** Русский · [🇬🇧 English version](../english/firewall.md)

## 📌 Описание

Модуль `firewall` управляет файрволом хоста через **nftables**. Демон владеет ровно одной таблицей — `inet asc` — и ничего другого не трогает: таблицы Docker, fail2ban и самого оператора остаются как есть (демон их только показывает, в режиме чтения).

Любое изменение применяется с **автоматическим откатом**: демон хранит то, что отменяет изменение, и выполняет это, если изменение не подтверждено до дедлайна. Правило, которое отрезает API демона или SSH, не запрёт оператора навсегда — как и потеря соединения: для подтверждения нужно рабочее соединение.

Для опытных есть **режим RAW**: весь ruleset сервера правится текстом. Он намеренно огорожен — требует явного подтверждения риска и использует тот же откат.

Всё работает автономно через `asc firewall …`; платформа AdminService.Cloud пользуется тем же API ([🧩 node-modules](../../../asc-platform/docs/features/node-modules.md)). Команде нужен работающий демон: таймер отката живёт внутри него. Файрволом управляет только системный (root) демон.

## 🎯 Сценарии использования

- 🔒 `sudo asc firewall enable` загружает `table inet asc` с политикой `drop` на входящие и правилами для SSH, API демона и (если установлен веб-сервер) HTTP/HTTPS — их демон выводит из состояния хоста, — затем просит подтвердить в течение 60 с.
- 🌐 `asc firewall allow 80,443/tcp` открывает веб-порты; `asc firewall allow 5432/tcp --from 10.0.0.0/8` открывает Postgres только для частной сети. При включённом файрволе изменение правила применяется сразу (с тем же окном подтверждения); `--no-apply` только сохраняет его.
- 🚫 `asc firewall deny --from 203.0.113.7` отбрасывает всё от одного адреса; `asc firewall set add blocklist 203.0.113.7 --ttl 24h` делает это на сутки и потом забывает. Блоклист защищает и опубликованные порты Docker.
- 🐳 Контейнер публикует `-p 8080:80`. NAT-правила Docker обходят цепочку `input`, поэтому правило со scope `docker` срабатывает в цепочке `forward` по исходному порту назначения: `asc firewall deny 8080/tcp --scope docker --from 203.0.113.0/24` действительно закрывает опубликованный порт. `asc firewall settings --protect-docker true` закрывает все такие порты, пока правило их не откроет.
- ⏱️ Оператор применил изменение по SSH и потерял соединение. Никто не подтвердил, дедлайн прошёл, прежние правила вернулись — связь восстановилась. После отката правка остаётся сохранённой: `asc firewall status` скажет, что есть неприменённые изменения.
- 🧑‍🔬 `asc firewall ruleset edit --i-understand-the-risk` открывает полный `nft list ruleset` в `$EDITOR`. Текст проверяется `nft -c` и применяется с тем же откатом.
- ⚠️ На хосте активен ufw или firewalld. `asc firewall enable` откажет и объяснит почему; `--force` выключает другое средство, но никогда не смешивается с ним.

## 🏗️ Техническое решение

Код: `src/daemon/firewall/`:

| Файл | Что делает |
|---|---|
| `model.rs` | Настройки, правила, наборы IP, валидация (порты, CIDR, протокол, комментарии) |
| `host.rs` | Факты о хосте (порты SSH из `sshd -T`, порт API, установлен ли веб-сервер) и выводимые из них пресеты |
| `render.rs` | Модель → текст `table inet asc`; детерминированно, счётчик на каждом правиле |
| `nft.rs` | Бинарь `nft` за трейтом: проверка `-c`, применение `-f`, листинги, счётчики из `-j` |
| `mod.rs` | Менеджер: сохранённая модель, применение, подтверждение, откат, таймер, восстановление после рестарта |
| `persist.rs` | `/etc/asc/firewall/ruleset.nft` и юнит `asc-firewall.service` |
| `conflicts.rs` | Находит активные ufw и firewalld |

### Режимы

| Режим | Смысл |
|---|---|
| `disabled` | Демон ничего не трогает; `table inet asc` удалена |
| `managed` | Демон владеет `table inet asc`, собранной из настроек и правил ниже |
| `raw` | Ruleset — текст оператора; управляемая модель хранится, но не применяется |

### Управляемая модель

- **Настройки**: `input_policy` (`accept` / `drop`), `allow_icmp`, `ipv6` (выключено — IPv6 не фильтруется), `protect_docker`, `disabled_presets`.
- **Правило**: `id`, `enabled`, `action` (`accept` / `drop` / `reject`), `protocol` (`tcp` / `udp` / `icmp` / `any`), `ports` (порты и диапазоны, только tcp и udp), `sources` (IP, CIDR, `@allowlist`, `@blocklist`; пусто — любой), `scope` (`host` / `docker` / `both`), `comment`.
- **Пресеты**: `ssh` (порты из `sshd -T`), `api` (порт API демона) и `web` (80/443, если установлен веб-сервер) выводятся при каждом применении, поэтому следуют за хостом. Выключить `ssh` или `api` можно только с `--force`.
- **Наборы**: `allowlist` и `blocklist` — nft-наборы с `flags interval,timeout`; у записи может быть срок действия.

### Рендер таблицы

Цепочка `input` (hook `input`, priority 0):

1. блоклист, затем отслеживание соединений (`established,related` разрешены, `invalid` отбрасываются) и loopback;
2. аллоулист, ICMP-ошибки и IPv6 neighbour discovery (всегда — без них ломаются IPv6 и path MTU discovery), ping, если разрешён, ответы DHCP;
3. правила-запреты (`drop` / `reject`), затем разрешения — порядок в списке не важен;
4. политика.

Цепочка `forward` (priority -1) есть, только когда она нужна (правило со scope `docker` или `both`, `protect_docker`, непустой блоклист). Каждое правило в ней сопоставляет `ct status dnat` и *исходный* порт назначения, поэтому исходящий трафик контейнеров не затрагивается; цепочки Docker демон не меняет. `drop` окончателен, `accept` лишь освобождает соединение от собственного `protect_docker`-запрета демона.

У каждого правила есть `counter` и комментарий `asc:<id>` — так счётчики пакетов сопоставляются с правилами.

### Применение с автооткатом

1. Скрипт отката записывается в `/var/lib/asc/firewall/pending.json` **до** изменений: прежняя `inet asc` (или `delete table`, если её не было); для RAW — весь `nft list ruleset`.
2. Новый ruleset проверяется `nft -c -f`, затем загружается атомарно (`table inet asc` + `delete table inet asc` + новая таблица в одной транзакции `nft -f`).
3. Запускается таймер (по умолчанию 60 с, допустимо 15–600 с; `--no-rollback` фиксирует сразу, для скриптов).
4. `confirm` фиксирует: скрипт становится `/etc/asc/firewall/ruleset.nft`, юнит включается, так что **после перезагрузки всегда возвращается последнее подтверждённое состояние**. По истечении дедлайна таймер выполняет скрипт отката.
5. Демон, перезапущенный в окне, доводит дело до конца: просроченное изменение откатывается, живое получает таймер обратно. Он же загружает подтверждённую таблицу, если ядро её потеряло.
6. Ждать подтверждения может только одно изменение.

### Режим RAW

`ApplyFirewallRuleset(text, acknowledge_risk)` отказывает без подтверждения, проверяет текст `nft -c`, затем выполняет `flush ruleset` и текст в одной транзакции с тем же откатом. Это заменяет **все** таблицы, включая Docker и fail2ban; откат восстанавливает их из дампа. Пока активен RAW, управляемая модель хранится, но не применяется. Выход из RAW (`disable`) оставляет то, что загрузил текст, до следующей перезагрузки.

### Персистентность

`asc-firewall.service` (`Type=oneshot`, `After=nftables.service`, `Before=network-pre.target`, создаётся демоном) загружает `/etc/asc/firewall/ruleset.nft` при старте. `/etc/nftables.conf` и `nftables.service` дистрибутива не трогаются; порядок после юнита дистрибутива важен: его конфиг по умолчанию начинается с `flush ruleset`.

### API (`FirewallService`)

| RPC | Что делает |
|---|---|
| `GetFirewall` | Режим, настройки, правила, пресеты, наборы, ожидающее изменение, конфликты, установлен ли `nft`, счётчики правил, неприменённые изменения |
| `InstallNftablesStream` | Ставит пакет, лог идёт потоком |
| `UpdateFirewallSettings`, `UpsertFirewallRule`, `RemoveFirewallRule`, `SetFirewallIpSet` | Правка модели (сохраняется, не применяется) |
| `RenderFirewall` | Таблица, которую загрузило бы следующее применение, рядом с действующей |
| `ApplyFirewall`, `ConfirmFirewall`, `RollbackFirewall`, `DisableFirewall` | Применить с окном, подтвердить, откатить сейчас, выключить |
| `GetFirewallRuleset`, `ApplyFirewallRuleset` | Режим RAW |
| `ListFirewallTables` | Все таблицы хоста, только чтение, с владельцем (`asc`, `fail2ban`, `iptables`, `other`) |

Capabilities в `GetStatus`: `firewall`, `firewall.raw`. Все вызовы — только от root. Те же операции доступны как REST под `/v1/firewall` для CLI.

### CLI

`asc firewall status | install | enable | disable | allow | deny | rules | remove | set | settings | render | apply | confirm | rollback | ruleset | tables`. Справочник команд: <https://docs.adminservice.cloud/ru/commands/firewall>.
