# 👤 Управление локальными пользователями

[🇬🇧 English version](../english/user-management.md)

## 📌 Описание

`UserService` — часть API демона (см. [📡 api](api.md)), дающая управление **локальными Linux-аккаунтами** ноды: список всех аккаунтов (включая root), создание и удаление, блокировка/разблокировка, смена логин-шелла, управление дополнительными группами (`sudo`, `docker`, ...) и разворачивание SSH-публичного ключа организации в `~/.ssh/authorized_keys` аккаунта. Это API за вкладкой «Users» на странице ноды платформы. В отличие от [📁 FileService](files.md), у `UserService` нет области видимости `app_id` — это администрирование аккаунтов всей машины, а не фича на приложение.

Демон никогда не работает с Linux-паролем: эта фича **только по SSH-ключам** по замыслу. `CreateUser` никогда не передаёт `-p` в `useradd`, так что свежесозданный аккаунт стартует с умолчанием самого `useradd` («без пароля» — хэш `!` в `/etc/shadow`) — вход становится возможен только после разворачивания ключа через `AddAuthorizedKey`.

## 🎯 Сценарии использования

- Платформа листает локальные аккаунты ноды для вкладки «Users»: `GET /v1/users`.
- Оператор заводит аккаунт для деплоя с доступом `sudo` и `docker`: `POST /v1/users {"name":"deploy","groups":["sudo","docker"]}`.
- Оператор приостанавливает аккаунт без удаления (например, при увольнении сотрудника): `PUT /v1/users/{name}/locked {"locked":true}`.
- Организация раздаёт участнику команды публичный ключ на общий аккаунт: `POST /v1/users/{name}/authorized-keys {"public_key":"ssh-ed25519 AAAA... alice@laptop"}` — повторный вызов с тем же ключом ничего не меняет, а не дублирует строку.
- Оператор отзывает один ключ, не трогая остальные: `DELETE /v1/users/{name}/authorized-keys {"fingerprint":"SHA256:..."}`.

## 🏗️ Техническое решение

### Область видимости и доступ

Как и `FileService`, `UserService` требует root-контекст вызывающего ([`UserContext`](../../src/daemon/apps/mod.rs)) для **каждого** метода (`users::require_root`): TCP-транспорт (платформа) всегда приходит с полными правами, а unix-сокет CLI — иначе доступный всем локальным пользователям — отдельно закрыт для не-root пира. Это администрирование аккаунтов всей машины, никак не разграниченное по вызывающему пользователю, поэтому здесь нет сужения в стиле `app_id`.

### Листинг и разбор

`ListUsers` разбирает `/etc/passwd`, `/etc/shadow` и `/etc/group` напрямую, независимо от собственного (более узкого) разбора `/etc/passwd`/`/etc/group` у `FileService`, который используется для выпадающего списка владельца в файловом менеджере, — баг в одном не должен задевать другой. Флаг `locked` берётся из поля хэша пароля `/etc/shadow`, начинающегося с `!` (включая вариант `!!`, который используют некоторые утилиты); `groups` содержит только **дополнительные** членства, разрешённые по спискам участников `/etc/group`, — группа, чей gid совпадает с основным gid аккаунта, исключается, даже если аккаунт там же явно указан участником. `is_system` — это `uid < 1000`: root (uid 0) присутствует в списке и помечен как системный, а не скрыт. Результат отсортирован по возрастанию uid.

### Создание и удаление аккаунтов

`CreateUser` вызывает `useradd`, а не правит `/etc/passwd` руками: дистрибутив-корректная работа с `/etc/shadow`, скелетон-файлами (`/etc/skel`) и NSS — именно то, для чего существует эта утилита. Каждая запрошенная дополнительная группа проверяется по `/etc/group` **до** запуска `useradd`, поэтому неизвестная группа отвечает типизированной ошибкой демона, а не stderr `useradd`. `home`, если задан, обязан быть абсолютным путём; `create_home` по умолчанию `true` (`useradd -m`, иначе `-M`).

`DeleteUser` вызывает `userdel` (`-r` при `remove_home`) и **жёстко отказывает на uid 0 и любом uid ниже 1000** — фиксированная подстраховка без обхода: это удаление Linux-аккаунта, а не записи платформы, и системные/сервисные аккаунты не в зоне ответственности этой фичи.

### Блокировка, шелл и группы

`SetUserLocked` запускает `usermod -L`/`-U`. На большинстве дистрибутивов с `UsePAM yes` в `sshd_config` заблокированный аккаунт отклоняется проверкой уровня account в `pam_unix` даже при успешной аутентификации по ключу — так что это реальный контроль «приостановить доступ» для аккаунта только по ключам, а не косметический флаг; точное поведение всё же зависит от настройки PAM дистрибутива.

`SetUserShell` требует, чтобы шелл был абсолютным путём, уже перечисленным в `/etc/shells`, — тот же allowlist, что использует сам `chsh`, — проверка идёт до запуска `usermod -s`.

`SetUserGroups` **заменяет** весь набор дополнительных групп, в стиле `usermod -G`, а не даёт API добавить/убрать: частичный API позволил бы двум операторам, меняющим группы одновременно, незаметно затереть изменения друг друга. Пустой `groups` очищает все дополнительные группы (`usermod -G ''`, а не пропуск флага). Каждая запрошенная группа проверяется по `/etc/group` до запуска `usermod`, как и в `CreateUser`.

### Authorized keys

Путь `~/.ssh/authorized_keys` аккаунта всегда вычисляется из его **разрешённого** домашнего каталога (свежий поиск по списку аккаунтов), никогда — из пути, присланного клиентом.

`ListAuthorizedKeys` возвращает пустой список, а не ошибку, если файла ещё нет — у свежего аккаунта его просто нет. Разбор распознаёт только строки, где первый токен — обычный префикс типа ключа (`ssh-`, `ecdsa-`, `sk-` — подавляющее большинство машинно-управляемых записей); строка, начинающаяся вместо этого со строки опций (например, `command="...",... ssh-ed25519 ...`), не разбирается, а строка, которая не смогла отфингерпринтиться (ручной мусор), пропускается, не обрушивая весь вызов. Фингерпринт каждого ключа (`SHA256:...`) берётся из `ssh-keygen -lf -`.

`AddAuthorizedKey` **идемпотентен**: добавление ключа, чей фингерпринт уже есть в файле, возвращает существующую запись без изменений вместо дублирования строки. Иначе создаётся `~/.ssh` (`0700`) и файл (`0600`), если их не было, оба переводятся на владельца аккаунта (uid/gid), и добавляется обрезанная строка ключа.

`RemoveAuthorizedKey` считает отсутствующий файл уже-удалённым состоянием (`Ok`, без ошибки) — тот же идемпотентный дух, что у `AddAuthorizedKey`. Файл переписывается атомарно (запись во временный `.tmp`-файл в том же каталоге, права исходного файла сохраняются, затем переименование поверх оригинала), владелец при перезаписи не трогается. Строка, которую не удалось разобрать как ключ (строка опций, ручной мусор), всегда остаётся нетронутой — совпадает она случайно или нет.

### 🗺️ Маршруты REST ↔ методы gRPC

| REST | gRPC | Описание |
|---|---|---|
| `GET /v1/users` | `UserService.ListUsers` | Все локальные аккаунты, включая root, по возрастанию uid |
| `POST /v1/users {"name","home"?,"shell"?,"create_home"?,"groups"?}` | `UserService.CreateUser` | Создание аккаунта через `useradd` |
| `DELETE /v1/users/{name}?remove_home=` | `UserService.DeleteUser` | Удаление через `userdel`; отказывает на uid 0 и любом uid ниже 1000 |
| `PUT /v1/users/{name}/locked {"locked"}` | `UserService.SetUserLocked` | Блокировка/разблокировка через `usermod -L`/`-U` |
| `PUT /v1/users/{name}/shell {"shell"}` | `UserService.SetUserShell` | Смена логин-шелла; обязан быть в `/etc/shells` |
| `PUT /v1/users/{name}/groups {"groups":[...]}` | `UserService.SetUserGroups` | Полная замена набора дополнительных групп |
| `GET /v1/users/{name}/authorized-keys` | `UserService.ListAuthorizedKeys` | Разобранные записи `authorized_keys`; строки-опции пропускаются |
| `POST /v1/users/{name}/authorized-keys {"public_key"}` | `UserService.AddAuthorizedKey` | Идемпотентное добавление |
| `DELETE /v1/users/{name}/authorized-keys {"fingerprint"}` | `UserService.RemoveAuthorizedKey` | Удаление по фингерпринту (в теле, не в пути — чтобы не URL-кодировать `/`) |

## 🔗 Связанные задачи

- DMN-099 — реализация `UserService` в демоне.
- Флаг возможностей `users` (см. `ApiState::CAPABILITIES`) включает вкладку «Users» на платформе — тот же приём, что у `sources`/`credentials`.
- [📁 files](files.md) — соседний общеузловой файловый API; `UserService` следует той же дисциплине root-доступа, но без области видимости `app_id`.
