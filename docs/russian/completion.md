# ⌨️ Автодополнение в шелле (Tab)

> 🌍 **Язык:** Русский · [🇬🇧 English version](../english/completion.md)

## 📌 Описание

Автодополнение `asc` по Tab в **bash**, **zsh** и **fish**: команды и подкоманды, флаги, значения-перечисления (`en|ru`, `on|off`, `cpu|mem`) и — то, чего не даст сгенерированная таблица — **живые значения**: установленные приложения, пакеты из кэша реестра, хранилища бекапов, источники реестра и сохранённые credentials. Аргументы, принимающие путь, возвращают работу шеллу: `asc backup storage add s3 --key /et<Tab>` дополняется до `/etc/` ровно так же, как `ls /et<Tab>`.

Установщик кладёт скрипты в системные каталоги; `asc completion <shell>` печатает их для ручной установки.

## 🎯 Сценарии использования

- 👤 Пользователь набирает `asc app st<Tab>` → `start` / `stop` (в zsh и fish — с однострочной подсказкой).
- 🚀 `asc app start <Tab>` → id приложений, которыми пользователю разрешено управлять: отвечает демон, поэтому обычный пользователь видит свои приложения, а root — все.
- 📦 `asc install nex<Tab>` → имена пакетов из кэша индекса реестра, без единого сетевого запроса и без подвисания на холодном кэше.
- 💾 `asc backup create myapp --storage <Tab>` → настроенные хранилища (`local`, бакет S3, SFTP-хост).
- 📁 `asc backup storage add s3 --key ~/.ssh/i<Tab>` → штатное дополнение путей самим шеллом.
- 🧑‍💻 Остановленный, недоступный или вовсе не установленный демон стоит нескольких кандидатов — но не ошибки и не зависшего Tab.

## 🏗️ Техническая реализация

### 🧩 Две команды

| Команда | Кто вызывает | Что делает |
|---|---|---|
| `asc completion bash\|zsh\|fish` | человек, установщик | печатает скрипт автодополнения для шелла |
| `asc __complete -- <words...>` | скрипт, на каждый Tab | печатает кандидатов для последнего слова |

Скрипты **не содержат собственного списка команд** (модель cobra — как у kubectl, gh и docker, а не сгенерированная таблица команд): они передают разобранную командную строку в `asc __complete` и печатают ответ. Поэтому новая команда, новый флаг или только что установленное приложение дополняются сразу — ничего не перегенерируется и не переустанавливается. Обе команды живут в [src/cli/complete.rs](../../src/cli/complete.rs); скрипты — в [completions/](../../completions/), в бинарь они попадают на этапе сборки.

### 📡 Формат обмена

`asc __complete` печатает по кандидату на строку, затем — необязательную директиву:

```text
start<TAB>Start the app and attach to its console
stop
:file
```

- `value<TAB>описание` — zsh и fish показывают описание вторым столбцом, bash берёт только значение.
- `:file` / `:dir` — «здесь пути»: шелл дополняет их сам (`compopt -o default`, `_files`, `__fish_complete_path`). Именно это сохраняет привычное поведение путей, включая завершающий `/` у каталогов.

Кандидаты фильтруются по набранному префиксу **внутри asc**, поэтому все шеллы получают одинаковый ответ.

### 🌳 Откуда берутся кандидаты

Движок обходит живое дерево команд clap, поэтому всегда соответствует своему бинарю: подкоманды и длинные флаги текущего уровня, варианты `ValueEnum` для перечислений, пути для аргументов с `ValueHint`. Поверх этого аргументы сопоставляются с **живыми списками** по месту в дереве и имени:

| Аргумент | Кандидаты | Источник |
|---|---|---|
| `id`, `app` (`asc app stop <id>`, `asc backup create <app>`, `asc auth add --app`) | установленные приложения | демон (`GET /v1/apps`), иначе локальное хранилище приложений |
| `spec` у `asc install`, `query` у `asc search` | пакеты | **кэш индекса** реестра — никогда не сеть |
| `spec` у `asc upgrade` | установленные приложения | как выше |
| `--source`, `asc source remove <name>` | источники реестра | `sources.toml` |
| `--storage`, `asc backup storage remove <name>` | хранилища бекапов | список хранилищ |
| `asc auth remove <target>` | сохранённые credentials | хранилище credentials |

Новая команда, называющая приложение `id` или `app` либо принимающая `--storage`, не требует правок в коде автодополнения.

### 🛡️ Правила движка

Автодополнение выполняется в шелле пользователя по нажатию клавиши — отсюда его ограничения:

- **Никогда не падает.** Нет демона, нет прав на сокет, нечитаемый `config.toml` — любой из случаев просто уменьшает список кандидатов. `asc __complete` обрабатывается *до* загрузки конфига и без подписчика tracing, поэтому сломанный конфиг не ломает Tab, а лог не попадает в приглашение шелла.
- **Никогда не блокирует.** У каждого динамического запроса бюджет 400 мс; зависший демон стоит одного пустого Tab, а не замороженного терминала.
- **Никогда не ходит в сеть.** Кандидаты реестра берутся только из кэша на диске. Обновляет кэш по-прежнему `asc update`.

### 📦 Установка

`asc-updater install` и `asc-updater update` пишут скрипты, запуская только что установленный бинарь (`asc completion <shell>`), — скрипт всегда соответствует установленному `asc`. Пишем только в уже существующие каталоги: их наличие и означает, что шелл на хосте есть:

| Шелл | Файл |
|---|---|
| bash | `/usr/share/bash-completion/completions/asc`, иначе `/etc/bash_completion.d/asc` |
| zsh | `/usr/share/zsh/vendor-completions/_asc`, иначе каталог `site-functions` |
| fish | `/usr/share/fish/vendor_completions.d/asc.fish` |

Весь шаг — best-effort: хост без zsh, `/usr` только для чтения или слишком старый `asc`, не знающий команду, никогда не ломают установку или обновление. Вручную:

```bash
asc completion bash | sudo tee /usr/share/bash-completion/completions/asc   # bash
asc completion zsh  | sudo tee /usr/share/zsh/vendor-completions/_asc       # zsh
asc completion fish | sudo tee /usr/share/fish/vendor_completions.d/asc.fish # fish
```

Новый шелл подхватит их сам; bash-completion загружает свой файл лениво, на первом `asc<Tab>`.
