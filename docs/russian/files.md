# 📁 Файловый API демона

[🇬🇧 English version](../english/files.md)

## 📌 Описание

`FileService` — часть API демона (см. [📡 api](api.md)), дающая обзор и управление файловой системой: список каталога, стат пути, создание каталога, перемещение/переименование, копирование, удаление, архивирование, потоковая загрузка и скачивание файла. По умолчанию область видимости — вся нода от корня `/` — это отдельный сервис от `AppService` и не заменяет [📁 SFTP-сервер](sftp.md), который даёт оператору собственный SFTP-клиент с изоляцией на каталог одного приложения. Каждый метод дополнительно принимает необязательный `app_id` (DMN-086), ограничивающий его каталогом и непубличными томами одного приложения — см. «Область видимости приложения» ниже. `FileService` — API и для файлового менеджера ноды платформы (браузерная вкладка «Файлы» на странице ноды), и, с `app_id`, для файлового менеджера приложения.

## 🎯 Сценарии использования

- Платформа листает каталог ноды и показывает его в браузере: `GET /v1/files?path=/etc`.
- Оператор загружает конфиг через вкладку «Файлы»: `PUT /v1/files/content?path=/etc/nginx/sites-available&name=app.conf`.
- Оператор скачивает файл: `GET /v1/files/content?path=/var/log/app.log`.
- Оператор архивирует несколько файлов перед скачиванием: `POST /v1/files/archive`.
- CLI/скрипты используют тот же REST напрямую с токеном, как и остальной API демона.

## 🏗️ Техническое решение

### Область видимости и доступ

Демон работает от root, и `FileService` видит всю файловую систему — платформа сама проверяет права пользователя (домен `files.read`/`files.edit`) до того, как запрос доходит до ноды. Из-за этого **каждый метод сервиса требует root-контекст вызывающего** и отвечает отказом иначе:

- на TCP-транспорте (платформа) контекст всегда полный — там это не ограничение;
- на unix-сокете CLI (`SO_PEERCRED`, [📡 api](api.md)) сокет намеренно доступен всем локальным пользователям (`0666`), и раньше это было безопасно только потому, что каждая операция шла через владельца приложения. `FileService` этому правилу не подчиняется, поэтому доступ к нему с сокета **отдельно закрыт для не-root пира** — обычный пользователь получает `403`/`PERMISSION_DENIED` на каждый файловый маршрут.

### Разрешение путей

Путь — абсолютный, без `..`, без NUL-байтов, в пределах разумных лимитов длины (4096 байт на путь, 255 байт на компонент), лексически нормализованный. Разрешение **намеренно не идёт через `canonicalize`**: эта функция резолвит финальный симлинк, а политика демона — «симлинк показываем, но не проходим через него». Имя файла при загрузке отдельно провалидировано: без слэша, без `..`, без NUL — оно приходит из браузера и не должно уметь выбирать каталог.

**Симлинки:** элемент каталога всегда отдаётся с типом `SYMLINK`, никогда с типом цели; вместе с ним — сырая цель (`symlink_target`) и, best-effort, тип цели (`target_kind`, отсутствует для битой ссылки). Рекурсивные операции (удаление, копирование, архивирование) **никогда не заходят внутрь** симлинка — та же дисциплина, что у обхода дискового пространства приложения и у бекапов. Удаление симлинка снимает саму ссылку, не трогая цель; копирование симлинка пересоздаёт ссылку, не копирует содержимое цели.

**Псевдо-корни `/proc`, `/sys`, `/dev`, `/run`:** листинг работает как обычно, но рекурсивные операции (удаление, копирование, архивирование) в них отказывают — размеры там фиктивны, а обход может зависнуть навсегда.

**Защищённые пути** (`/`, `/boot`, `/etc`, `/usr`, `/var`, `/asc`) отказывают как точная цель разрушающей операции — это подстраховка от промаха, а не граница безопасности: root на машине всё равно может сделать то же самое руками.

### Область видимости приложения (DMN-086)

Каждый метод выше дополнительно принимает необязательный `app_id`. Если он задан, вызов становится **ограниченным приложением** вместо общеузлового: вызывающему достаточно владеть приложением (`AppManager::get_authorized` — та же проверка владения, что и у любого другого метода на приложение, включая root), а не иметь root-контекст, и каждый путь в вызове ограничивается собственным каталогом приложения (`<apps_dir>/<id>`) плюс его непубличными (не общими) томами (`AppScope`, построенный из той же классификации томов, что использует `GetAppDisk`, — именованный Docker-том исключается, поскольку может быть смонтирован и в другие приложения).

Ограничение проверяется **на стороне демона**, безусловно — оно не делегируется вызывающей стороне. Это важно, потому что TCP-транспорт всегда приходит с полными правами (платформа сама проверяет право пользователя до того, как запрос доходит до ноды), поэтому пользователь платформы с `apps.edit`, но без `files.edit`, обязан оставаться структурно неспособным дотянуться до чего-либо за пределами своего приложения через этот путь. В отличие от неограниченного разрешения пути выше, ограниченный приложением путь **канонизируется**: самый глубокий уже существующий предок запрошенного пути резолвится через каждый встреченный симлинк до проверки на принадлежность области — так симлинк, подложенный внутри каталога приложения (`data/escape -> /etc`), не может стать способом прочитать или записать что-то за пределами области. Ещё не существующий хвост пути (например, создаваемый файл) дописывается буквально — там пока ничего нет, и симлинком он быть не может.

Ответ `GetAppDisk` несёт для этой цели уже разрешённый `app_dir` — платформа не может вычислить `<apps_dir>/<id>` сама, поскольку корень хранилища демона нигде отдельно не публикуется.

См. [📁 app-file-manager](../../../asc-platform/docs/features/app-file-manager.md) — фичу платформы, которую это разблокирует.

### Потоковая передача

`ReadFile` — server-stream чанками; `WriteFile` — client-stream чанками с заголовком (`каталог`, `имя`, `overwrite`, режим) в первом сообщении. Размер чанка — **256 КиБ**: далеко под лимитом декодирования gRPC-сообщения (4 МиБ по умолчанию), достаточно крупный, чтобы не тонуть в overhead на syscall и HTTP/2-фрейм.

Загрузка пишется во временный файл рядом с целевым (`.asc-upload-<случайное>.part`, права `0600`), синхронизируется на диск и переименовывается на место — та же дисциплина атомарной записи, что у сохранения токена. Оборванная загрузка не оставляет обрезанный файл там, где был целый: временный файл просто остаётся `.part` и убирается при следующей попытке или уборке. Без `overwrite` коллизия имени проверяется **до** первого принятого байта.

### Архивирование

Только формат `tar.gz` (`tar` + `flate2`, уже в зависимостях демона). Формат `zip` зарезервирован в протоколе и отвечает `UNIMPLEMENTED` — добавление `zip`-кодировщика усложнило бы cross-сборку под aarch64/armv7 отдельным набором зависимостей, а минимальность зависимостей — правило проекта. Архив содержит ровно запрошенные имена, без единого элемента-симлинка внутри.

### Лимиты

Листинг каталога ограничен **10 000 записями**; при превышении ответ несёт `truncated: true` и `total_entries`.

### Права доступа и владелец

`SetPathAttributes` меняет режим и/или владельца/группу — семантика `chmod`/`chown`: несданное поле не трогается, а не сбрасывается в умолчание. Владелец и группа задаются **именем**, не числовым uid/gid — вызывающая сторона это UI-выпадашка, а не скрипт; имя резолвится в id через `/etc/passwd`/`/etc/group`. Смена владельца символической ссылки идёт по ссылке (как обычный `chown`, не `chown -h`) — файловый менеджер оперирует тем, во что путь резолвится.

`ListSystemIdentities` отдаёт список локальных пользователей и групп машины — источник для выпадающего списка при смене владельца. Разбирает `/etc/passwd`/`/etc/group` напрямую, а не через `getpwent`/`getgrent`: у тех нет истории потокобезопасности, а разбор файла руками ей и не нужен. Доступ, как и весь остальной сервис, только для root-контекста — не потому что сам список чувствителен (имя владельца и группы и так видно в каждой записи `ListDirectory`), а потому что сервис в принципе не разграничен по вызывающему пользователю.

### 🗺️ Маршруты REST ↔ методы gRPC

| REST | gRPC | Описание |
|---|---|---|
| `GET /v1/files?path=&hidden=&app_id=` | `FileService.ListDirectory` | Список каталога; `hidden=true` показывает dotfiles |
| `GET /v1/files/stat?path=&app_id=` | `FileService.StatPath` | Метаданные одного пути |
| `POST /v1/files/directory {"path","parents","app_id"?}` | `FileService.CreateDirectory` | Создание каталога |
| `POST /v1/files/move {"source","destination","overwrite","app_id"?}` | `FileService.MovePath` | Перемещение/переименование |
| `POST /v1/files/copy {"source","destination","overwrite","app_id"?}` | `FileService.CopyPath` | Копирование |
| `POST /v1/files/delete {"paths":[...],"recursive","app_id"?}` | `FileService.DeletePaths` | Удаление; best-effort — один отказ не прерывает остальные |
| `POST /v1/files/archive {"directory","names","archive_path","format","app_id"?}` | `FileService.CreateArchive` | Архивирование в `tar.gz` |
| `GET /v1/files/content?path=&offset=&app_id=` | `FileService.ReadFile` (стрим) | Скачивание, с поддержкой возобновления по `offset` |
| `PUT /v1/files/content?path=&name=&overwrite=&app_id=` | `FileService.WriteFile` (стрим) | Загрузка |
| `POST /v1/files/attributes {"path","mode"?,"owner"?,"group"?,"app_id"?}` | `FileService.SetPathAttributes` | Смена режима и/или владельца/группы (по имени) |
| `GET /v1/files/identities` | `FileService.ListSystemIdentities` | Локальные пользователи и группы машины — только общеузлово, без `app_id` |

`app_id` (query-параметр в REST, поле в каждом gRPC-запросе выше) везде необязателен: не задан — общеузловое поведение, описанное выше в документе; задан — ограничение приложением (см. выше).
