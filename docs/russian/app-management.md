# 📱 Управление приложениями (демон)

## 📌 Описание

Ядро демона: единый интерфейс управления приложениями трёх типов — 🐳 Docker-контейнеры, 📦 нативные приложения (systemd-юниты) и 🔧 обычные процессы (PID). Ключевое отличие от Portainer/Coolify: не только Docker.

## 🎯 Сценарии использования

- `asc app install helloworld` — установка из реестра (Docker или нативное — решает манифест).
- `asc app start|stop|restart|status|logs <name>` — управление жизненным циклом. `asc app kill <name>` — принудительная остановка SIGKILL без корректного завершения, для приложения, которое не реагирует на `stop`; её можно вызвать, пока `stop` ещё ждёт, — тот вернётся, как только приложение умрёт. `start` сразу подключается к консоли приложения (Docker-приложения, интерактивный терминал — как `docker run` без `-d`); `asc app start -d <name>` запускает в фоне, без подключения. Если хосту не хватает ресурсов, заявленных в `requirements` манифеста, `start` предупреждает с цифрами и спрашивает, продолжать ли на свой страх и риск.
- **Пользовательские названия**: `asc install` спрашивает название приложения (Enter — по умолчанию; неинтерактивно — `--name`). `asc app list` показывает и оригинальный ID, и NAME, а все команды принимают и то и другое: `asc app start "My Server"` = `asc app start cs2-server`. При совпадении названия с чужим id приоритет у id; неоднозначное название (несколько одинаковых) — ошибка с подсказкой использовать id. И id, и название сравниваются **без учёта регистра** — id канонически в нижнем регистре (`HOMEBAR` ставится как `homebar`, см. [📦 package-manager](package-manager.md)), поэтому `asc app start HOMEBAR` до него доходит; точное написание по-прежнему приоритетнее приведённого к регистру, так что два названия, отличающиеся только регистром, остаются адресуемыми.
- **Несколько инстансов одного приложения**: повторная установка уже установленного пакета больше не завершается ошибкой — создаётся новый инстанс `<пакет>-2`, `<пакет>-3`, … (он же становится названием по умолчанию), поэтому `asc install nginx` дважды даёт два независимых приложения `nginx`/`nginx-2`. Повторная установка целого стека называет новые инстансы так же; `--name <префикс>` при установке целого стека называет по этому же принципу каждое приложение-участник, так как у стека нет собственной сущности.
- **`asc app disk <имя>`**: дисковое пространство — прогресс-бар против квоты, если задан `quota.max_disk`, затем разбивка по Docker-образу, репозиторию, приватным данным и кастомным томам (именованные тома Docker помечены как общие и не входят в сумму по каталогу приложения).
- **Версия образа и repull**: **`AppService.GetAppImage`** сообщает, на каком образе работает Docker-приложение — ссылка, тег, версия (лейбл `org.opencontainers.image.version`, иначе тег, если он не `latest`), локальный дайджест манифеста из `RepoDigests` и id образа, из которого создан контейнер, — а с `check_remote` ещё и дайджест, который реестр отдаёт для тега сейчас (`/distribution/{name}/json` через Engine: запрос манифеста без слоёв, таймаут 15 с, те же креды реестра, что при установке). Вердикт: `RESTART_REQUIRED`, если тег уже указывает на более новый локальный образ, чем у контейнера, иначе `UP_TO_DATE`/`UPDATE_AVAILABLE` по дайджесту, иначе `UNKNOWN` (локальная сборка, образ не скачан или реестр не ответил). **`AppService.RepullApp`** заново скачивает образ из реестра с тегом `latest` (или без тега) и перезапускает запущенное приложение, если образ изменился; закреплённый тег, дайджест, локальная сборка или не-Docker приложение отвергаются с `FAILED_PRECONDITION`. Отдельного пути пересоздания для рестарта не нужно: drift-проверка настроек (`pkg::refresh`) теперь сравнивает id образа контейнера с id, на который указывает ссылка, поэтому любой старт/рестарт после pull — в том числе после ручного `docker pull` — пересоздаёт контейнер на новом образе, как `docker compose up`. Capability `app.repull`. **`AppService.RepullAppStream`** — тот же repull живой лентой: строки скачивания слоёв образа, затем тот же `RepullAppResponse`, — чтобы платформа вела repull как фоновую задачу с логом; отключившийся клиент его не отменяет. Capability `app.repull.stream`.
- **`asc app clone <имя> [--name <имя-клона>]`**: полная копия инстанса приложения — репозиторий, config и data — под новым id (та же нумерация `<id>-N`, что и при повторном `asc install`), с живым прогресс-баром копирования в терминале. Сам рантайм не копируется (Docker-контейнер/systemd-юнит/процесс скопировать нельзя) — он пересоздаётся заново из скопированного манифеста и настроек, точно как при установке. Клон всегда стартует остановленным. **`AppService.CloneApp`/`CloneAppStream`** отдают ту же операцию по gRPC/REST (`POST /v1/apps/{id}/clone`) для кнопки «Клонировать» на платформе; потоковый вариант репортит прогресс копирования текстовыми строками (по одной на каждый целый процент) — точно как `InstallAppStream`/`UpgradeAppStream`. Клонирование на *другую* ноду переиспользует это локально, на целевой ноде, как фазу «установка» межнодового переноса — см. 🧬 app-cloning. Этому переносу нужно заново собрать спецификацию установки из собственных метаданных приложения — точно так же, как это уже делает внутри себя `asc app upgrade` (`meta.source`/`meta.package`/`meta.repo_path`/`meta.branch`), поэтому `App` (`ListApps`/`GetApp`) теперь несёт ещё `package`, `repo_path` и `branch` рядом с уже существующими `source`/`version`/`commit` — все опциональные, все отсутствуют у приложения, установленного прежней версией.
- **`asc app rebuild <имя> [--service <сервис>] [--no-pull]`** (алиас `asc rebuild`): заново скачать или собрать образы приложения и принудительно пересоздать его контейнеры **без смены версии** — «та же ссылка, git pull, пересборка» после того, как исправление запушено в ветку, за которой следит приложение, или базовый образ получил обновление безопасности. По умолчанию сначала подтягивается ссылка, за которой приложение уже следит; `--no-pull` это пропускает; `--service` пересобирает один сервис docker compose-приложения (и подразумевает `--no-pull`). Только docker- и docker compose-приложения. См. **🧱 Пересборка** ниже.
- **Сервисы docker compose-приложения**: `asc app services <имя>` показывает все сервисы с состоянием, health, образом и портами; `--service <сервис>` у `asc app logs|start|stop|restart|kill` действует на один сервис вместо всего проекта. Остановка сервиса временная — следующий старт, пересборка или обновление приложения поднимают его снова. Настройки сервиса (окружение, лимиты CPU/памяти, политика перезапуска) переживают обновления. См. **🧩 Сервисы docker compose-приложения** ниже.
- `asc app list` — пользователь видит **только свои** приложения; `sudo asc app list` — приложения всех пользователей. Короткие алиасы: `asc ls` и `asc ps` — тот же вывод и те же права.
- **`asc ports [<имя>]`** / **`asc app ports [<имя>]`**: опубликованные порты приложения с транспортом (`27015/tcp`, `27015/udp` или `27015/tcp+udp`, когда оба на одном порту), взятые из настроек `type: ports` — поэтому **остановленное** приложение всё равно показывает порты, которые оно займёт при следующем старте. Пакет, который фиксирует свою контейнерную сторону (`container:`), показывается как `8080->3000/tcp`: сначала хостовый порт, затем контейнерный за ним. Без имени — таблица всех видимых приложений с их портами (root видит приложения всех пользователей). **`AppService.ListAppPorts`** — тот же список по gRPC, для платформы: docker-приложения возвращают свои порты, остальные виды — пустой список.
- `asc stats [--live] [--sort cpu|mem]` — потребление CPU, памяти, диска и сети по приложениям (аналог `docker stats`, см. [📊 monitoring](monitoring.md)).
- **Подкоманды списка**: `asc ls ports`, `asc ls disk` и `asc ls stats` переключают тот же список приложений на вид портов, использования диска или живой статистики — зеркала `asc ports` / `asc disk` / `asc stats`.
- **`asc stacks`**: установленные приложения, сгруппированные по стеку (`asc.stack.yaml`), из которого они пришли, деревом — имя стека с пометкой, сколько его приложений сейчас запущено (`[running/total]`), затем его приложения ветками `├──`/`└──` (id, name, kind, state, version, uuid — те же колонки, что и в `asc ls`), root видит приложения всех пользователей. Стек определяется по `meta.package` (`"<стек>/<приложение>"`, записывается при установке — см. [📦 package-manager](package-manager.md)); у приложения, установленного самого по себе, в `package` нет `/`, и оно сюда не попадает.
- Платформа выполняет те же операции через API демона.
- После ребута сервера демон восстанавливает состояние приложений (running/stopped).

## 🏗️ Техническое решение

### 👥 Группы приложений по пользователям

- Каждое приложение принадлежит Linux-пользователю, который его установил (владелец фиксируется в `meta.json` и индексе).
- Обычный пользователь видит и управляет **только своей группой приложений**.
- Через `sudo` (или от `root`) видны и доступны приложения **всех пользователей** — вывод группируется по владельцам.
- API демона применяет то же правило: контекст запроса определяет видимую группу.
- **При работающем системном демоне** команды жизненного цикла (`ls`/`status`/`install`/`app start|stop|restart|logs|remove|info`) идут через его unix-сокет `/run/asc/asc.sock`: демон берёт uid вызывающего у ядра (SO_PEERCRED) и применяет это правило к общему системному стору — обычный пользователь управляет своими приложениями в `/asc/apps` **без sudo и без группы docker**, а `asc ls` и `sudo asc ls` наконец показывают одно и то же. Подробнее — [📡 api](api.md).
- **Отчётные команды идут тем же маршрутом**: `asc disk`, `asc ports`, `asc stats`, `asc stacks` и `asc upgrade` тоже ходят через сокет. Раньше они читали in-process *своё* дерево приложений вызывающего, поэтому пользователь, чьи приложения лежат в системном дереве, видел их в `asc ls` и «Приложения не установлены» во всех отчётах рядом — а `asc app upgrade <id>` отвечал «приложение не найдено» для приложения, которое очевидно есть. In-process остались `asc app clone` и `asc backup`: им по-прежнему нужен прямой доступ к системному дереву (root или отсутствие демона).

### 📂 Хранилище приложений: /asc/apps/

Каждое приложение живёт в каталоге по своему ID:

```
/asc/apps/<id>/
├── .asc/              # 🔒 собственные файлы демона — не видны в обычном `ls`
│   ├── meta.json      # 📇 информация о приложении: id, uuid, имя, пользовательское название, владелец, версия (тег), источник, отслеживаемая ветка, состояние
│   └── settings.json  # ⚙️ выбранные значения настроек (см. asc.settings.yaml в package-manager.md)
├── repository/        # 📦 клонированный репозиторий приложения (версии — git-теги)
└── data/              # 💾 volumes — если приложение в Docker
```

- **Установка = клонирование репозитория** пакета в `repository/`; переключение версии — checkout нужного git-тега (подробнее — [📦 package-manager](package-manager.md)).
- `.asc/meta.json` — источник правды для восстановления индекса после сбоя/ребута.

#### 🔒 Служебный каталог `.asc/`

Свои файлы по приложению демон хранит в скрытом каталоге `.asc/` — в каталоге приложения видно только то, что относится к самому приложению (`repository/`, `data/`, папки томов). Меняйте эти файлы через `asc` (`asc app settings`, `asc app rename`, …) — ручная правка может нарушить работу CLI и управление приложением с платформы; файловый менеджер платформы предупреждает об этом и просит принять риски перед любым изменением внутри `.asc/`.

- **Миграция**: у приложений, установленных прежней версией, `meta.json` лежал в корне каталога, а значения настроек — в `config/settings.json`. При первом чтении такого приложения демоном или CLI оба файла переезжают в `.asc/` (сначала настройки, последним meta — прерванный перенос просто повторится) и опустевший `config/` удаляется; всё остальное, что пользователь положил в `config/`, остаётся. Если перенести нельзя (например, обычный пользователь читает дерево без права записи), файлы читаются со старых мест и приложение продолжает работать.
- `.asc` — зарезервированное имя папки тома; `config` и `meta.json` больше не зарезервированы.
- **Разделение путей по пользователям**: `/asc/apps/` (вместе с `/etc/asc/config.toml` и `/var/lib/asc`) — дерево **root**-установки: системный демон и `sudo asc`. Запуск `asc` от обычного пользователя **без работающего системного демона** работает со своим приватным деревом в `~/.asc/`: `~/.asc/apps`, `~/.asc/data`, `~/.asc/config.toml` — так пользователь редактирует настройки своих приложений и конфиг без sudo. При наличии демона команды жизненного цикла работают с общим системным деревом через сокет демона (см. выше). Root-секция `[policy]` по-прежнему читается из системного конфига и не переопределяется на уровне пользователя.

#### 🗃️ Локальная база: индекс приложений

Демон ведёт локальную базу установленных приложений — SQLite в `<data_dir>/index.db` (`/var/lib/asc/index.db` у системного демона, `~/.asc/data/index.db` у обычного пользователя без демона; права `0600`, журнал WAL). В ней зеркало **всего содержимого `.asc/` каждого приложения**: `meta.json`, разложенный по колонкам для поиска, и содержимое каждого другого файла верхнего уровня — `settings.json`, `compose.override.yaml`, `compose.override.orphaned.yaml` и всего, что появится там позже, — с отпечатком файла, из которого оно прочитано (`inode:size:mtime:ctime`, поэтому замечается даже файл, подменённый с сохранённым mtime). Там же — коммит, на котором стоит `repository/`.

- **Зачем**: `asc ls`, `/v1/apps`, `ListApps` и `GetStatus` берут список приложений из базы — без чтения `meta.json` и без `git rev-parse` на каждое приложение, — а любая команда CLI проверяет связь с демоном через `GET /v1/health`, а не полным списком приложений. Планировщик бекапов раз в минуту читает политики всех приложений из зеркала `settings.json`, а не из файлов. Состояния рантаймов опрашиваются пачкой: один список контейнеров Engine на все docker- и compose-приложения, один `systemctl show` на все systemd-юниты, проверка pid у process-приложений.
- **Источник истины — по-прежнему файлы.** На них опираются бекапы, клонирование и ручное восстановление; база производна от них и всегда пересобирается. Операция над одним приложением (`start`, `upgrade`, …) по-прежнему читает его собственный `meta.json`.
- **Синхронизация с файлами**: любая запись демона или CLI идёт сначала в файл и сразу же — в базу; inotify-watcher (Linux) на каталоге приложений, каталоге каждого приложения, его `.asc/` и `repository/.git` пересинхронизирует приложение, изменённое в обход демона (правка файла руками, восстановленный каталог); демон сверяет базу с файлами раз в минуту и при старте — только `stat`, без чтения файлов. CLI без демона сверяет базу перед чтением списка.
- **Не зеркалируются**: `op.lock` (блокировка операции), временные `*.tmp` недописанной атомарной записи, симлинки и подкаталоги — в `.asc/backups/` лежат копии файлов *репозитория* пользователя, сохранённые при обновлении, а не состояние приложения. Файл больше 1 МиБ попадает в базу без содержимого.
- **Самовосстановление**: нет базы, сменилась схема или `apps_dir` → полная пересборка из файлов при старте; повреждённый файл (или записанный более новым демоном) откладывается как `index.db.broken-<ts>`, и база собирается заново. Удалить `index.db` можно в любой момент.
- **`asc db status`** — путь к базе, версия схемы, каталог приложений, сколько в ней приложений и файлов, размер, когда её последний раз пересобирали и сверяли; **`asc db verify`** — сверить с файлами и исправить расхождения; **`asc db rebuild`** — собрать заново. Только root — через демон (`GET /v1/db`, `POST /v1/db/verify`, `POST /v1/db/rebuild`), если он запущен, иначе напрямую с файлом.
- **Аварийный выключатель**: `ASC_NO_INDEX=1` в окружении `asc` (или юнита демона) оставляет прежний обход файлов.

#### 🆔 UUID инстанса

Кроме `id`, каждый инстанс получает **UUID**, который генерируется при `asc install` и хранится в `meta.json` в поле `uuid`. Он переживает upgrade и выводится последней колонкой `asc ls`:

```
ID          NAME        KIND     STATE       VERSION  UUID
pingpong    Ping Pong   docker   stopped     0.1.0    6f8a1c2e-3b4d-4e5f-8a9b-0c1d2e3f4a5b
legacy-app  Legacy App  docker   stopped     1.2.0    -
```

Зачем второй идентификатор: `id` **переиспользуется**. После удаления `helloworld-2` этот id освобождается для следующей установки — и всё, что живёт дольше приложения (сохранённые учётные данные, записи платформы, история аудита), молча привязалось бы к другому приложению. UUID уходит вместе с инстансом и никогда не выдаётся повторно.

- Генерируется как случайный UUIDv4 (RFC 4122) из `/dev/urandom` — ради шестнадцати байт не тянем отдельную зависимость.
- **Необязателен в `meta.json`**: у приложений, установленных прежней версией, ключа `uuid` нет — они читаются как обычно и показывают `-`. Ничего не дописывается втихую.
- `asc app clone` выдаёт клону **свой** UUID — это отдельный инстанс, а не копия идентичности.
- В API отдаётся как `App.uuid` (поле proto 10, REST `uuid`), отсутствует, если не задан.

### 🐳 Контейнеры хоста

`asc docker ps` показывает **все** контейнеры хоста, а не только установленные
через ASC, а `asc docker stats` — их живые CPU и память. Обе команды идут через
Engine API, как и весь драйвер, и обе доступны **только root**: у контейнера,
созданного не через ASC, нет владельца, по которому работает проверка прав, —
значит, не-root вызывающего не к чему привязать.

- Контейнер, который *является* приложением ASC, помечается как таковой. Связь
  выводится из runtime в `meta.json` самого приложения, а **не** поиском
  префикса `asc-` в имени контейнера: этот префикс — соглашение об именовании,
  которого придерживается демон, а не заявка на владение, и оператор волен
  назвать так же контейнер, поднятый руками.
- Лейблы Compose `com.docker.compose.project` / `.service` поднимаются из общей
  карты лейблов в отдельные поля, чтобы вызывающему не приходилось знать, как
  именно Compose пишет свои ключи.
- **Размеры запрашиваются явно** (`asc docker ps -s`, `size=1`): чтобы ответить,
  Engine обходит writable-слой каждого контейнера — на загруженном хосте это
  заметная пауза и лишняя работа для того, кому нужен просто список.
- **Статистика — отдельный вызов**, а не колонка списка. Процент CPU требует
  двух замеров с интервалом ~500 мс, и список не должен платить эту цену при
  каждом открытии — ровно то же разделение уже есть у `asc ls` и `asc stats`.
  Оба замера делаются вокруг одного общего сна, поэтому пятьдесят контейнеров
  стоят тех же ~500 мс, что и один, а фильтр по id применяется *до* окна, а не
  после.
- Контейнер, исчезнувший между двумя замерами, просто отсутствует в результате:
  это штатная гонка, а не ошибка вызова.

**Управления жизненным циклом здесь намеренно нет.** Контейнер приложения ASC
нельзя запускать и останавливать мимо менеджера приложений — `desired_state`
сверяется после перезапуска демона, контейнер вернётся сам, и оператор прочтёт
это как баг; для этого есть `asc app start|stop`. У чужого контейнера вообще нет
модели прав — это отдельная задача со своей capability.

### 🧹 Инвентарь хоста и очистка

`asc docker images|volumes|networks|df` расширяют инвентарь хоста за пределы
контейнеров: все образы, именованные тома и сети, которые знает Engine, плюс
сводка `df` по образцу `docker system df`. `asc docker prune
images|volumes|build-cache [--dry-run] [--dangling]` удаляет неиспользуемое —
и никогда не трогает то, что всё ещё нужно установленному приложению.

- **Образ или том, который объявляет установленное приложение, защищён —
  запущено оно или нет.** Защищённое множество считается по манифесту и
  настройкам каждого приложения (образ, к которому оно сейчас разрешается
  через `runtime.image`/`runtime.image-build`, и каждый именованный том из
  настройки `type: volumes`), а не по лейблам или соглашению об именах.
  `asc docker images`/`volumes` помечают защищённую строку и называют
  приложение, которое её держит.
- **Удаление — поштучное, никогда не через собственный массовый
  `/images/prune` или `/volumes/prune` Engine.** У контейнера, созданного не
  через ASC, нет лейбла-владельца, поэтому массовая очистка с фильтром либо
  ничего не отфильтрует (без фильтра) и рискует гонкой удалить что-то
  используемое, либо фильтрует по лейблу, который демон начал ставить только
  в новых версиях, и тогда образ любого ранее созданного контейнера остаётся без
  защиты. Поштучное удаление делает проверку защищённого множества точной, а
  `--dry-run` — отчётом о том, что случится на самом деле, а не оценкой.
- **Сети — только инвентарь, `asc docker prune networks` не существует.** ASC
  никогда не создаёт и не удаляет сети сам, а собственный prune сетей у
  Engine сносит любую сеть без *запущенных* контейнеров — включая сеть
  остановленного compose-стека, что молча ломает его следующий `up`. Показ
  сетей без пути удаления полностью обходит эту ловушку.
- **`asc docker df` не дешёвый и никогда не опрашивается.** Как и `docker
  system df`, ответ заставляет Engine обойти каждый слой образа и каждый том;
  вызывать его при открытии раздела очистки, не по таймеру.
- **Лейблы контейнера** (`asc.managed`, `asc.app.id`, `asc.app.uuid`)
  начиная с этой версии пишутся на каждый контейнер, который создаёт ASC, — на
  будущее, для вызывающего, которому нужно опознать ASC-контейнер без
  сравнения имени. Они чисто информационные: проверка дрейфа настроек
  (`container_applied`) лейблы никогда не читает, поэтому их появление не
  может вызвать нежелательное пересоздание уже работающего контейнера.

### 🧱 Пересборка

`AppService.RebuildApp` / `RebuildAppStream` (`pkg::rebuild`), REST `POST /v1/apps/{id}/rebuild {"service"?, "pull_source"?}`, CLI `asc app rebuild` / `asc rebuild`, MCP-инструмент `app_rebuild`. Capability `app.rebuild`.

- **docker compose, весь проект** — шаги обновления compose на месте (см. [📦 package-manager](package-manager.md)): с `pull_source` подтягивается ссылка, за которой приложение уже следит (HEAD его ветки, тег, на котором оно закреплено — тег не двигается, поэтому коммит остаётся прежним, — или HEAD ветки по умолчанию), и выкатывается checkout, локальные правки сохраняются заранее; затем проверки, `pull`/`build --pull`, пока старые контейнеры работают, и `up --force-recreate`. Без `pull_source` подтягивание пропускается. `meta.version`/`meta.branch` не меняются; сбой откатывается так же, как у обновления.
- **docker compose, один сервис** — `build --pull <сервис>` (есть `build:`) или `pull <сервис>`, затем `up -d --no-deps --force-recreate <сервис>` (`--no-start`, если сервис не запущен). Остальные сервисы не трогаются. `service` вместе с `pull_source` — `INVALID_ARGUMENT`: один сервис пересобирается из тех исходников, что уже есть у приложения.
- **docker** — с `pull_source` и движущейся ссылкой (ветка, за которой следит приложение, или ветка по умолчанию репозитория без тегов у прямой установки), чей коммит в репозитории отличается от установленного, приложение останавливается, обновляется на ту же ссылку (обычное обновление клоном рядом — данные лежат вне `repository/`) и потом запускается снова; у приложения на теге или из реестра подтягивать нечего. Затем образ: готовый скачивается **с любым тегом** (repull умеет только `latest`), собираемый пересобирается с `pull` (свежий базовый образ); контейнер пересоздаётся (`refresh::recreate`) и запускается, если работал.
- **systemd / process** — пересобирать нечего: `NotRebuildable`, `FAILED_PRECONDITION` (в REST — 409).
- **Состояние сохраняется**: желаемое состояние не меняется; остановленное приложение остаётся остановленным, но контейнеры пересозданы. `RebuildAppResponse` сообщает, какие сервисы пересобраны, коммит до и после, сдвинулись ли исходники (`source_updated`) и запущено ли приложение.
- **Одна операция за раз**: пересборка, как и обновление, держит блокировку операции приложения (`.asc/op.lock`); вторая из двух получает `FAILED_PRECONDITION`.
- **Живой прогресс**: `RebuildAppStream` отдаёт вывод git, pull и build событиями `line` и заканчивается тем же `RebuildAppResponse`; закрытие стрима отменяет пересборку на ближайшей контрольной точке (само пересоздание всегда доводится до конца).

### 🧩 Сервисы docker compose-приложения

`AppService.ListAppServices`, `ControlAppService`, `GetAppServiceSettings`, `SetAppServiceSettings` (`apps::compose_services`), capability `app.services`. Каждый из них отвечает `INVALID_ARGUMENT` для приложения, которое не docker compose, и `NOT_FOUND` для сервиса, которого нет в проекте.

- **Откуда данные.** Имена сервисов — те, что последний раз вернул `docker compose config --services` (`Runtime::Compose.services`; у старого приложения разбираются сами compose-файлы). Контейнеры — из **bollard**, `list_containers` с фильтром по метке `com.docker.compose.project`; сервис без контейнера — `missing`; health — статус healthcheck контейнера. Одноконтейнерный вид показывает первую реплику — сначала запущенную. С `with_stats` один общий замер ~500 мс охватывает только запущенные контейнеры этого приложения (тот же сэмплер, что у `list_container_stats`, но без требования root: вызывающий владеет приложением).
- **Список приложений несёт сводку.** `App.compose_services` (`name`, `state`, `health` по сервисам) заполняется из **одного** списка контейнеров bollard на весь вызов `ListApps`, он же даёт состояние каждого compose-приложения — без `docker compose ps` на каждое приложение.
- **Действия** (`ControlAppService`, `asc app start|stop|restart|kill <app> --service <s>`): stop, restart и kill действуют на контейнеры сервиса через bollard; start тоже, а для сервиса без контейнера выполняет `up -d --no-deps <сервис>`. `desired_state` приложения не трогается — остановка сервиса временная. `DockerService.ControlContainer` по-прежнему отказывает контейнерам ASC-приложений.
- **Логи** (`GetAppLogsRequest.service`, `asc app logs <app> --service <s>`): один контейнер читается через bollard; несколько реплик — через `docker compose logs --no-log-prefix <сервис>`. В обоих случаях без префикса имени сервиса, который есть у лога всего проекта.
- **Настройки — override-файл демона.** `<app_dir>/.asc/compose.override.yaml` (`apps::compose_override`): собственный файл демона, вне `repository/` и git, `0600` и с владельцем каталога приложения (значения окружения могут быть секретами), передаётся плагину последним `-f`. В нём только `environment`, `deploy.resources.limits.{cpus,memory}` и `restart` — без `volumes`, `ports`, `build` и `env_file`, поэтому он не может расширить bind-монтирования и не содержит относительных путей. Если файл пакета задаёт лимиты старыми ключами `cpus:`/`mem_limit:`, override использует те же ключи (compose отказывает, когда лимит задан обоими способами). Каждый `$` в значении записывается удвоенным, чтобы compose его не интерполировал.
  - **Валидация**: сервис существует; имена переменных соответствуют `[A-Za-z_][A-Za-z0-9_]*`; `cpus` > 0 и не больше ядер хоста; память не меньше 6 МиБ; `restart` — `no`, `always`, `on-failure[:N]` или `unless-stopped`.
  - **Запись**: временный файл → `config -q` по проекту с ним → атомарный `rename`; записанные имена сервисов обновляются. Запись держит блокировку операции приложения.
  - **Применение**: с `apply` запущенный сервис, чьи настройки изменились, пересоздаётся отдельно (`up -d --no-deps --force-recreate <сервис>`, `applied`); иначе запущенный сервис сообщает `restart_required`, а остановленный подхватит настройки при следующем старте.
  - **Чтение**: `GetAppServiceSettings` возвращает то, что задаёт override, и итоговые значения, которые compose разрешает с ним, — только **имена** переменных, никогда их значения.
  - **Обновления и бэкапы**: checkout файл не трогает; записи сервисов, исчезнувших из compose-файлов, переносятся в `.asc/compose.override.orphaned.yaml`. Бэкап архивирует файл рядом с `settings.json`, восстановление возвращает его.

### ⚙️ Ядро

- **Драйверы**: трейт `AppDriver { start, stop, kill, restart, state, logs, remove }` (`kill` — SIGKILL: `docker kill`, `docker compose kill`, `systemctl kill --signal=SIGKILL`, kill процесса; безопасен параллельно с идущим `stop`) с реализациями `DockerDriver` (через **Docker Engine API поверх unix-сокета** — не через `docker` CLI; путь сокета настраивается — `[docker] socket`, по умолчанию `/var/run/docker.sock`), `SystemdDriver` (юниты `asc-app-<id>.service`), `ProcessDriver` (supervised PID: pid-файл и лог-файл в каталоге приложения). Установка приложения (создание контейнера/юнита из манифеста) — зона пакетного менеджера.
- **Docker Engine API**: демон общается с Docker через Engine API (клиент `bollard`, unix-сокет), а не через CLI — это работает и для rootless-инсталляций, и при нестандартном расположении сокета (достаточно указать путь в конфиге). Управляющие операции (start/stop/inspect/create/remove) — синхронные; стрим логов и attach для консоли — асинхронные по тому же сокету. Создание контейнера само скачивает образ, если его нет на хосте (pull через тот же Engine API); ответ Engine с любым HTTP-статусом не считается недоступностью Docker — пользователю показывается сообщение самого Engine.
- **Индекс приложений**: `meta.json` — источник правды; список приложений берётся из локальной базы (SQLite, см. **🗃️ Локальная база** выше), которая синхронизируется с файлами при каждом изменении и сверяется с ними. При старте демон открывает (или пересобирает) базу, затем сверяет желаемое состояние (`desired_state`) с реальностью (контейнеры, юниты, процессы) и дозапускает упавшее.
- **Логи**: единый интерфейс — docker logs / journald / файл; стрим наружу через [🖥️ console](console.md).
- **Cluster-мод (пост-MVP)**: несколько *узлов*, работающих вместе как платформа. Несколько инстансов одного приложения на одном узле уже работают (выше).
- **CLI-команды MVP**: `asc status`, `asc stats`, `asc ports`, `asc stacks`, `asc rebuild`, `asc app list|install|remove|start|stop|restart|logs|info|disk|ports|clone|settings|rebuild|services` (+ алиасы `asc ls`/`asc ps` для списка и `asc ls ports|disk|stats` для видов портов/диска/статистики), `asc service` (управление самим демоном), `asc db status|verify|rebuild` (локальная база), `asc docker ps|stats|images|volumes|networks|df|prune` (контейнеры, образы, тома, сети хоста и очистка).
